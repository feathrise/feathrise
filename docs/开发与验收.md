# 开发与验收

## 桌面文件窗口专项

使用原开发缓存执行 `cargo build --locked --features validation`，再以 `--file-manager-report <新的绝对路径.json>` 运行生成程序。该入口独占创建中性工程和归属标记，隔离个人偏好与插件，经正式右键／新建二级菜单、窗口输入及文件服务验证整理流程，并验证活动资产窗的筛选、片段、预览、共享缩略图与原搜索收藏服务。报告同时核对窗口状态、后台回执、新建 TXT／MD／GLB 的解析与退出后磁盘回读，以及真实 GPU PNG；运行后须查看图片。普通构建不安装此驱动，内部输入不替代实体键鼠／系统拖放验收。

Windows 开发动态链接验收使用 EXE 实际导入的 Bevy DLL 和当前工具链 std DLL。本轮将三项复制到带 owner 的独占运行目录并逐文件核对 SHA-256；以本次进程的 `FEATHRISE_EDITOR_ROOT` 指定原源码资源根、`--target-dir` 指定原 `target/`。没有改变系统 PATH、SDK、profile 或构建缓存。仅补 PATH 的启动在本机未进入 Rust 主程序，不计为功能验收。

$sceneTreeGlbReport = Join-Path (Get-Location).Path ('target/scene-tree-choose-glb-' + [Guid]::NewGuid().ToString('N') + '.json')

## 依赖与本地源码

当前源码使用 Bevy 0.20.1 及已锁定的公开 SDK、补丁。按 [README](../README.md#从源码启动)可直接构建，也可选择本地联调。消费工程在自己的 `[patch.crates-io]` 配置八项补丁。

### 本地源码覆盖

把 [本地编译示例](../.cargo/local-sdk.example.toml) 复制为 `.cargo/local-dev.toml`，并在需要联调新建工程时把 [模板来源示例](../sdk-source.local.example.toml) 复制为 `sdk-source.toml`。三个公开仓默认同级检出，两个示例中的路径可按各自位置调整。

编辑器单独检出时使用 `Cargo.toml` 和根目录的 `Cargo.lock` 固定公开 Git 依赖。启用本地配置后，Cargo 按示例中的 `resolver.lockfile-path` 将锁写入已忽略的 `.local/sdk/Cargo.lock`。先在编辑器目录执行 `cargo fetch` 准备联调锁，再运行定向检查。恢复公开依赖时移出或改名 `.cargo/local-dev.toml`，公开锁可直接使用。

旧的 `.cargo/local-sdk.toml` 不会自动加载。更新已有检出后，从新示例创建 `.cargo/local-dev.toml`，把原有自定义 `[patch.crates-io]` 路径移入并保留 `[resolver]`。旧配置与联调锁均可留在本机。

```powershell
cargo check --locked -p feathrise_host -p feathrise_editor_scene -p feathrise_editor_ui --tests
cargo test --locked -p feathrise_host --lib
```

测试字体通过 SDK 的公开 `DEFAULT_FONT_BYTES` 获取。需要文件路径的独占夹具自行写入这份字节，不读取 SDK 仓库内部文件。原生运行库身份通过轻量 `feathrise_runtime_manifest` crate 获取，默认编辑器无需为读取清单启用 DLSS 或安装厂商 SDK。

特性通过 Cargo `--features` 选择：`fsr` 启用 FSR 超分与帧生成候选，须先将 `FEATHRISE_FSR3_PACKAGE` 指向与 SDK 锁匹配的本地 Windows 原生 ZIP；可选 DLSS 帧生成需要额外厂商 SDK 与桥接构建环境。开发沿用已有 `target/` 和当前 profile，例行检查无需清缓存。

### 内嵌资源与跨检出缓存

普通 Cargo 构建从工作树内的 `assets/` 读取资源。调用者用外部缓存目录编译时，为该次 Cargo 进程设置 `BEVY_ASSET_PATH` 指向当前工作树的 `assets/` 绝对路径。

项目 `.cargo/config.toml` 为当前检出自动绑定 `FEATHRISE_BUILD_SOURCE_ROOT`，构建脚本同时跟踪此来源根与 `BEVY_ASSET_PATH`。切换源码目录并复用同一个 `target/` 时，即使新检出的资源、清单或 `Cargo.lock` 时间戳较旧，也会重新生成资源身份；相同字节继续得到相同内容身份，不把机器路径混入资源缓存名称。无改动构建仍可复用现有产物，无需清缓存或手工更新 `build.rs` 时间戳。

源码版新建工程默认读取 [templates/empty](../templates/empty/) 的源码、Cargo 清单和锁。它是独立 Cargo 工程。启用了编辑器本地覆盖时，在编辑器仓库的父目录检查公开模板，使 Cargo 从当前目录查找配置：

```powershell
cargo check --locked --manifest-path feathrise/templates/empty/Cargo.toml --target-dir feathrise/target
```

发行单 EXE 的模板由打包器在构建完成后提供。显式 `sdk-source.toml` 可为新建工程选择其他 SDK 来源。

Cargo 的 `--manifest-path` 不会自动加载目标项目的配置。从其他目录构建宿主时，须同时加载该检出的配置，例如：

```powershell
cargo run --locked --manifest-path 'C:\src\feathrise\Cargo.toml' --config 'C:\src\feathrise\.cargo\config.toml'
```

来源绑定缺失或指向其他检出时，构建会明确拒绝。正常进入编辑器源码目录再执行原有命令即可；无需修改用户全局环境。

普通 `cargo run` 将本仓的 `LICENSE-MIT`、`LICENSE-APACHE` 和 `THIRD_PARTY_NOTICES.md` 内嵌进编辑器，可在「工程 → 关于 Feathrise → 许可与署名」查看。

## Windows 发布构建

已有开发环境时，从编辑器目录执行 `cargo build --release` 编译，用 `cargo run --release` 启动。

当前源码发行构建也使用配套的本地 SDK 与补丁覆盖。发行工具生成合并后的许可纯文本，通过绝对路径 `FEATHRISE_LICENSE_DOCUMENT` 交给 `cargo build-windows-release`。此入口关闭 Bevy 动态链接，静态链接 C 运行库，并内嵌许可。发布取经过导入核对的 `feathrise.exe`，收件人可在编辑器「关于 → 许可与署名」阅读。日常使用的 Bevy 动态链接由默认特性 `bevy_dynamic_linking` 选择。

## 可选自有品牌构建

当前公开源码不附带 Feathrise 正式 Logo。未设置 `FEATHRISE_BRANDING_DIR` 时，编辑器正常构建，不内嵌正式 Logo，也不读取其他目录中的品牌文件。

需要自有品牌时，准备一个含以下两个文件的目录，并确保自己拥有使用和分发这些素材的权利：

| 文件名 | 构建用途 |
| --- | --- |
| `feathrise-mark.png` | 内嵌的界面品牌图片 |
| `feathrise.ico` | Windows 可执行文件图标 |

将 `FEATHRISE_BRANDING_DIR` 显式设为该目录的绝对路径，再执行原有构建命令。例如：

```powershell
$env:FEATHRISE_BRANDING_DIR = 'C:\my-branding'
cargo run --locked
```

设置后，两份文件都必须存在；目录不存在或缺少规定文件时构建会报错，不会静默改用其他品牌素材。恢复无 Logo 构建时，移除该环境变量并重新构建。此入口不提供正式 Logo，也不授予 Feathrise 的名称或标识使用权；既有副本和官方原版程序继续遵循[品牌使用条件](../THIRD_PARTY_NOTICES.md#feathrise-品牌使用条件)。

## Blender 导出器

[保存导出脚本](../crates/feathrise_editor_assets/src/blender_export/Blender保存时自动导出GLB.py)由共享资产 crate 在编译时内嵌。建模与 Blender 绑骨在各自的后台会话中释放并调用同一份脚本。普通构建和地形 GLB 保存无需安装 Blender。建模与 Blender 绑骨使用本机 Blender 自带的 Python 和 glTF 工具。

调试导出器时，可将 `FEATHRISE_BLENDER_TOOLS_DIR` 设为含同名脚本的绝对目录。绑骨也支持专用覆盖 `FEATHRISE_RIG_BLENDER_TOOLS_DIR`，优先于共用覆盖。移除覆盖即可使用当前构建内置的脚本。

## 函数体热更新工具

Windows 函数体热更新使用已验证的 `dx 0.7.9`。官方单文件发行内嵌 DX 和配对运行库，首次 DX 构建在后台解压到当前工程 `target/hotpatch-tools/embedded-dx-0.7.9/` 的内容缓存并校验，后续自动复用。源码构建者可在构建时通过 `FEATHRISE_DX_BUNDLE` 提供包含官方 `dx.exe` 与 `vcruntime140.dll` 的绝对目录。开发者仍可用 `FEATHRISE_DX_PATH` 显式覆盖。未内嵌的源码版编辑器可从资源根父目录下的 `dx-path.txt` 读取一行 DX 可执行文件绝对路径。没有路径文件时，仍可使用该父目录下的 `.local/hotpatch/tools/dx-0.7.9/dx.exe`。

链接代理源码归本仓 `assets/hotpatch/原生热补丁链接代理.rs`，随固定资源清单编译内嵌。源码开发从编辑器资源根读取，安装版从同一内容身份的资源缓存读取；生成的链接代理仍进入所选工程构建缓存，不读取父仓库的 `tools/` 源码。资源搬移与缓存校验测试覆盖该文件，实际函数更新仍需对应的真实运行验收。

## 中性验收

真实窗口验收仅在显式 `validation` 下安装；普通构建不安装自动操作或故障注入。各场景只创建自己的新夹具工程，核对原交互、后台回执、保存落盘、重开和实际截图。

```powershell
cargo run --locked -p feathrise_host --features validation -- --scene-format-report <新的绝对报告路径.json>
cargo run --locked --features validation -- --native-report <新的绝对报告路径.json>
cargo run --locked --features validation -- --embedded-report <新的绝对报告路径.json>
cargo run --locked --features validation -- --embedded-build-cancel-report <新的绝对报告路径.json>
cargo run --locked --features validation -- --code-iteration-report <新的绝对报告路径.json>
cargo run --locked --features validation -- --export-report <新的绝对报告路径.json>
```

场景格式、停止编译、代码迭代和导出入口需要 Windows。场景格式专项创建两个场景和子场景引用，保存启动项，重开同一工程并验证预览、导出和独立运行。报告旁的 `.work` 目录保存各阶段回执和截图。各报告以实际执行的阶段为准。编译检查、内部输入及旧报告不替代实体键鼠、系统对话框、其他平台或完整人工验收。

导出默认场景核对 `output/` 与包的搬移运行；为本次进程设置 `FEATHRISE_EXPORT_VALIDATION_SCENARIO=custom-cancel-retry` 可追加自选目录、取消保留和重试流程。

## 工程自有插件场景

专属模型、规则、安装器和场景由工程仓库维护。需要原宿主内部控件的配套验收时，可在 `validation` 构建中将 `FEATHRISE_VALIDATION_EXTENSION` 设为外部 Rust 适配器的绝对路径。

适配器以宿主内部子模块编译，提供 `run(target, report, package)` 和 `install(app, project)`，分别接管 `--plugin-report` 及作者实例的验收安装。它依赖对应宿主源码版本，不是稳定作者插件 ABI。构建脚本只在显式 `validation` 下读取配置并监听适配器子模块；普通构建忽略该变量。

默认公开构建没有适配器，也不读取工程仓库。未配置时 `--plugin-report` 明确报错，不生成成功报告。通用插件协议、管理器、保存及中性作者回归仍在本仓维护；工程负责其夹具及验收证据。
